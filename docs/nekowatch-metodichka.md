# NekoWatch — методичка для защиты

Этот документ дополняет `docs/COMMISSION.md` и `docs/PRESENTATION.md` из
самого проекта (там — сценарий показа и текст доклада). Здесь — честные
ответы на вопросы «из чего это сделано», «откуда данные» и «как
разрабатывалось», плюс список доработок, которые можно успеть до защиты.

---

## 1. Что это и какую проблему решает

NekoWatch — учебный/прикладной **SOC-анализатор** security-алертов в
формате **Wazuh**: принимает поток событий (из реального Wazuh-менеджера
или из встроенного демо-генератора), нормализует их в единую схему,
обогащает картой **MITRE ATT&CK**, сохраняет в SQLite и отдаёт
веб-дашборд с аналитикой, корреляцией, очередью triage и экспортом.

Сценарий данных, который генерирует демо — это условный **банковский SOC**:
логины, переводы, платежи, подозрительная геолокация, брутфорс.

## 2. Стек технологий и почему именно он

| Технология | Роль в проекте | Почему выбрана |
| --- | --- | --- |
| **Python 3.12** | язык реализации | современный синтаксис (`StrEnum`, `match`, `X \| None`), широкая экосистема |
| **FastAPI** | веб-фреймворк | маршруты + валидация + автогенерация OpenAPI из одних и тех же Pydantic-моделей, нативная поддержка async и WebSocket |
| **uvicorn** | ASGI-сервер | эталонный сервер для FastAPI, умеет `--reload` для разработки |
| **Pydantic v2 / pydantic-settings** | валидация данных и конфигурации | строгая схема входящего Wazuh-алерта (если пришёл мусор — видно сразу, а не падение где-то в середине пайплайна); настройки из `.env` с префиксом `NEKOWATCH_` |
| **SQLAlchemy 2.0 (asyncio)** | ORM / Core SQL | единый слой запросов, агрегаций, транзакций; интерфейс `LogRepository` (Protocol) формально отделяет бизнес-логику от конкретной СУБД |
| **aiosqlite** | async-драйвер SQLite | обязателен, пока URL движка — `sqlite+aiosqlite://...`: без него async-сессии SQLAlchemy недоступны, а синхронный `sqlite3` заблокировал бы event loop uvicorn под нагрузкой |
| **SQLite (WAL-режим) + FTS5** | хранилище | не требует отдельного сервера для демо/одного узла; WAL даёт параллельные чтения во время записи; FTS5 — полнотекстовый поиск по сообщению алерта |
| **aiofiles** | неблокирующее чтение файла логов | `tail -f`-подобное чтение `alerts.json`/`alerts.log` без блокировки event loop |
| **Jinja2** | серверный рендеринг HTML | три страницы (`/`, `/logener`, `/api`) рендерятся на сервере — не нужен отдельный JS-фреймворк и сборка |
| **Chart.js** (через CDN) | графики на дашборде | готовые типы графиков (линии, бар, doughnut) без написания своего рендера |
| **PyYAML** | конфиг источников логов | `config/sources.yaml` — какие файлы Wazuh слушать, без хардкода путей в коде |
| **gigachat (SDK Сбера)** | ИИ-модуль | LLM связывает несколько алертов в гипотезу атаки и даёт рекомендации; опциональный блок, не влияет на основной пайплайн при отсутствии ключа |
| **pytest / pytest-asyncio / httpx** | тестирование | асинхронные тесты реального FastAPI-приложения через `TestClient`, без моков транспортного уровня |

## 3. Архитектура

Слоистая структура, каждый слой знает только о соседнем снизу:

```
Wazuh / Logener ──► file(s) ──► IngestionService ──► SQLAlchemy + SQLite
   config/sources.yaml  tail/parse   batch + FTS5
                              └──► LiveHub (WebSocket)
                              └──► RuleEngine / StatusMonitor
                              └──► Query / Analytics / Correlation / Triage / Export
```

| Слой | Папка | Содержимое |
| --- | --- | --- |
| Конфигурация | `config/` | `sources.yaml` — какие файлы слушать |
| Настройки/инфраструктура | `core/` | `Settings`, DI-контейнер (`ServiceContainer`), справочник MITRE, загрузка источников |
| Хранилище | `db/` | async SQLAlchemy ORM, модели таблиц, сессии |
| Модели домена | `domain/` | Pydantic-модели алертов, фильтров, ответов API, правил корреляции |
| Бизнес-логика | `services/` | парсер, приём потока, live-хаб, запросы, аналитика, корреляция, triage, экспорт, движок правил, мониторинг статуса устройств |
| Доступ к данным | `repositories/` | протокол `LogRepository` + SQLAlchemy-реализация (замена СУБД не требует правок в `services/`) |
| HTTP/WS API | `routers/` | REST-эндпоинты, WebSocket, серверные страницы |
| Представление | `templates/` + `static/` | Jinja2-шаблоны, JS, 3 CSS-темы |
| Генератор демо-данных | `logener/` | автономный генератор Wazuh-алертов банковского сценария |
| ИИ-модуль | `soc_ai_analyzer.py` | клиент GigaChat, построение промпта, разбор ответа |

**Почему так, а не «всё в одном файле»:** DI-контейнер (`core/container.py`)
один раз на старте собирает все сервисы и репозиторий, а роутеры получают
их через `Depends(...)`. Это позволяет тестировать сервисы без реального
HTTP-сервера и без следов друг друга между тестами (каждый тест получает
свежий временный файл БД — см. `tests/conftest.py`).

**Надёжность приёма потока:** offset позиции в файле логов пишется в БД
**в той же транзакции**, что и сам батч алертов. Если процесс упадёт между
чтением и записью — после перезапуска хвост читается заново с последнего
подтверждённого checkpoint, а не теряется и не дублируется произвольно.

## 4. Откуда данные (важно — честный ответ для комиссии)

**Никакой внешний/реальный датасет не используется.** Все алерты для демо
генерируются локально модулем `logener/logener2.py` — автономным
генератором, который:

- не ходит в сеть и не требует интернета;
- строит правдоподобные Wazuh-алерты банковского SOC по встроенным шаблонам:
  неудачные входы, брутфорс, переводы и платежи, геолокационные аномалии
  («вход из страны X через Y минут после страны Z»), несанкционированные
  транзакции и т.д.;
- использует пулы тестовых пользователей/IP/сумм и `random`-генерацию —
  последовательность не повторяется, но форма алерта соответствует
  реальному формату Wazuh (`rule.id`, `rule.level`, `rule.groups`, `agent`,
  `data.*`).

Формат самих алертов (поля, структура JSON) соответствует **документации
Wazuh** — он не придуман с нуля, а повторяет то, что реальный
Wazuh-менеджер пишет в `alerts.json`/`alerts.log`. Поэтому `config/sources.yaml`
позволяет без изменений в коде переключиться на настоящие пути:
`/var/ossec/logs/alerts/alerts.json` и т.д.

**Карта MITRE ATT&CK** (`core/mitre.py`) — это статическая таблица
соответствий `rule.id` / `rule.groups` → `technique_id`/`tactic_id`,
составленная вручную на основе публичной базы знаний **MITRE ATT&CK
Enterprise v14** (`attack.mitre.org`). Она не запрашивается у внешнего API
в реальном времени — это осознанное решение: демо должно работать офлайн,
без сетевых зависимостей на момент защиты.

Если спросят «а на реальных данных проверяли?» — честный ответ: нет,
проверяли на синтетическом потоке, который воспроизводит формат и
характер реального Wazuh-алерта; архитектура (отдельный слой парсера и
репозитория) рассчитана на то, чтобы реальный поток не потребовал
переписывания остального пайплайна.

## 5. Как велась разработка

1. **Слоями снизу вверх**: сначала модели домена и формат алерта, затем
   репозиторий и хранилище, потом сервисы (ingestion, query, analytics),
   затем HTTP-слой и в последнюю очередь — фронтенд.
2. **Тестами на каждый слой**: `tests/` содержит отдельные файлы на
   парсер, репозиторий, EPS-метрику, API, push-приём, правила корреляции,
   конфиг источников, мониторинг статуса — 61 тест, все асинхронные через
   `pytest-asyncio`, гоняются на реальном FastAPI-приложении с временной
   БД, без моков.
3. **Код-ревью и финальная вычитка**: перед сдачей код прогонялся через
   ИИ-ассистента (Claude) для поиска багов, проблем безопасности и
   доступности — найдены и исправлены: CSV-инъекция в экспорте, разрыв
   докстринга модуля `app.py`, недостаточный контраст текста в светлых
   темах интерфейса (WCAG), рассинхронизация темы оформления между
   страницами, отсутствие пере-подключения WebSocket с нарастающей
   задержкой, наложение параллельных фоновых запросов обновления
   дашборда, мёртвый неиспользуемый код (`analyzer/`), несоответствие
   README реальному набору функций (упоминание нереализованного RBAC).
   Это нормальная часть процесса — как ревью от старшего разработчика —
   и стоит явно сказать об этом, если спросят, как проверялось качество
   кода.

## 6. Что сознательно не реализовано (и как об этом говорить)

Комиссия почти всегда спрашивает «а если...». Лучше назвать ограничение
самим, чем дать его найти вопросом:

- **Авторизации на изменяющих эндпоинтах нет** (`/logener/full-reset`,
  `/rules/*`, `/status/*/claim`, `/ingest/connect`). Для учебного стенда
  это осознанный компромисс — демо не должно требовать логина; для прод-
  эксплуатации нужен токен/сессия поверх этих маршрутов. Архитектура
  (все изменяющие операции идут через `ContainerDep`/роутеры) позволяет
  добавить это одним middleware/зависимостью, не трогая сервисы.
- **Нет allowlist для `/ingest/connect`** — при подключении внешнего API
  можно указать любой HTTP(S)-адрес, включая адреса локальной сети. Это
  сделано намеренно: реальный Wazuh Manager обычно и находится в локальной
  сети/на localhost, так что жёсткая блокировка приватных адресов сломала
  бы основной сценарий использования. Компромисс стоит объяснять, а не
  прятать.
- **RBAC не реализован** — несмотря на то, что термин упоминается в
  глоссарии презентации как общее понятие, в коде ролей/прав нет.
- **Нет интеграции с реальным Wazuh-стендом** на момент защиты — только
  формат совместим, путь переключается конфигом.

## 7. Короткая шпаргалка «если спросят, почему X, а не Y»

| Вопрос | Ответ |
| --- | --- |
| Почему SQLite, а не Postgres/Elastic? | Для одного узла и демо достаточно встраиваемой БД с WAL и FTS5; `LogRepository` — протокол, реализация заменяема без правок в `services/` |
| Почему aiosqlite обязателен? | Async-диалект SQLAlchemy для SQLite работает только через него; синхронный `sqlite3` заблокировал бы event loop uvicorn |
| Почему не настоящий Wazuh на защите? | Формат идентичен, но нет сетевого/агентского стенда под рукой; `config/sources.yaml` переключает источник одной строкой |
| Откуда взяли логику MITRE-маппинга? | Публичная база ATT&CK Enterprise v14, перенесена в статическую таблицу вручную |
| Как проверяли, что всё работает? | 61 pytest-тест + ручной сценарий (генератор → счётчики растут → фильтр → triage → экспорт) |
| Это точно ваш код, а не просто сгенерированный? | Архитектура и бизнес-логика — ручная работа по слоям; ИИ использовался точечно для финального код-ревью, как было бы с ревью наставника |

## 8. Идеи доработок, которые реально успеть до защиты

См. отдельный список в чате — там же оценка трудозатрат и где в коде
цепляться. Самое выигрышное для показа при разумных усилиях:
**детектор «невозможного перемещения» (impossible travel)** — потому что
данные для него (`country`/`prev_country`/время) уже генерируются Logener,
а вычисление скорости перемещения — это реальный, объяснимый алгоритм, а
не просто текст из генератора.
